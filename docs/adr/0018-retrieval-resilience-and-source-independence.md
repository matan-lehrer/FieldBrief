# 0018. Bounded search-engine testing and fingerprint-based source independence

- **Status:** Accepted
- **Date:** 2026-10-23

## Context
Two related retrieval-quality gaps. First: this project's own heavy dev-time query volume rate-limited SearXNG's main engines — Brave and Google CSE are "Suspended: too many requests" and DuckDuckGo requires a CAPTCHA SearXNG can't solve, leaving `bing` (added in an earlier round) as the only consistently-working general engine. Second, unrelated to engine health: nothing distinguishes a press release syndicated across several domains from several genuinely independent sources agreeing — `content_hash` is exact-match and scoped to one URL, so three copies of one release on three domains could inflate `Confidence.corroboration` to 3.

## What was actually tested (not assumed)
Live-queried the running SearXNG instance directly (not through the app) with several real and nonsense queries. Confirmed: Brave/Google CSE/DuckDuckGo remain down (same as the prior round's finding, not a regression). Checked SearXNG's own bundled engine defaults for other free, no-key options: **startpage** and **mojeek** both ship `inactive: true` upstream specifically because they now require a proof-of-work CAPTCHA SearXNG can't automate — enabling them would just add a request that always fails, not real capacity. **marginalia** returned zero results across three realistic test queries ("Wix competitors", "Quicklizard company", a nonsense query) — no observed value. **wikipedia** returned a real, useful background link (the company's own Wikipedia page) on a branded query, at zero cost and zero risk — kept. Also confirmed the previously-diagnosed bias is still present: four different phrasings of a "Wix competitors" query ("competitors alternatives", "vs Squarespace", "compare hub squarespace") returned the *identical* 10 URLs in the *identical* order through Bing — branded-query results dominated by the brand's own domain regardless of query intent, a real, currently-unresolved limitation of relying on one scraped engine. "Quicklizard company" (an obscure company), by contrast, now resolves correctly to the real company's own pages — that part of the regression (per Matan's original complaint about VAST Data/Quicklizard) is confirmed fixed by the entity-resolution work earlier in this round, independent of the engine-health issue.

## Decision
- `searxng/settings.yml`: keep `bing` + add `wikipedia`. Explicitly did not add startpage/mojeek (dead ends, confirmed via their own upstream config) or marginalia (confirmed zero value via live testing, not assumption).
- `fetch/clean.py` gains `content_fingerprint()`: lowercase, strip to alphanumerics, hash the first 500 normalized chars — cheap, bounded, catches near-duplicate syndicated text without new infrastructure (deliberately not a MinHash/simhash library — the actual failure mode observed is near-identical press-release text, which an exact-after-normalization hash already catches).
- New nullable `Source.content_fingerprint` column (append-only; never backfilled for existing rows). `reports/confidence.py`'s corroboration count now groups claims by fingerprint (falling back to source id when unknown) instead of by raw source id — a syndicated release contributes one independent fact, not N.
- **Deliberately not done in this pass, to avoid building unwired infrastructure:** making `Fetcher.fetch()` return a richer failure reason (403/timeout/robots-disallowed vs. 404) so gaps could show "inaccessible" distinctly from "not found". The fetch layer already collapses every failure to `None`, and that's a real limitation per Matan's "record retrieval failures" ask — but threading it into `gap_check_node`'s reason taxonomy needs per-field failure-reason aggregation across multiple URLs that isn't needed by anything else right now. Building that abstraction with no real consumer violates the project's own "no speculative abstractions" rule. Left as a clearly-named follow-on, not silently dropped.

## Consequences
- Corroboration bonuses are now harder to earn when sources are more connected to the same original text — a real strengthening of confidence scoring, not just a cosmetic change.
- Bing remaining the sole general engine is an accepted, documented limitation, not a fixed problem — competitor discovery for a well-known brand can still be starved of comparison content by Bing's own branded-query ranking. This isn't something another SearXNG engine config change can fix today; it would need a different data source (e.g. a paid search API) or a smarter query/result-filtering strategy, either out of scope for a free-stack constraint or its own future stage.
- When we would revisit this: if Brave/Google CSE recover (rate limits reset) or a genuinely working free alternative engine is found, re-test rather than assume Bing-only is permanent. If the fetch-failure-reason gap becomes a real blocker (e.g. a report consistently mislabels a paywalled source as "not found" and that's confusing in practice), build `Fetcher`'s richer result then, with a real consumer in the same change.
